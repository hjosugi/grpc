## フレームワークの役割

`grpc.NewServer()` がHTTP/2接続とRPC dispatchを担当します。
`RegisterShopServiceServer` はprotoから生成され、Goの実装をRPC名に結び付けます。
`UnimplementedShopServiceServer` の埋め込みは、サービスにメソッドを追加した際の前方互換性を助けます。
GinなどのHTTP routerはこのRPCサーバーには不要です。

## Unaryを追う

```go
func (s *Server) PayOrder(ctx context.Context, r *pb.PayOrderRequest) (*pb.Payment, error) {
    if err := ctx.Err(); err != nil {
        return nil, status.FromContextError(err).Err()
    }
    return s.Store.Pay(r)
}
```

`ctx` はdeadlineやcancelの通知を持ちます。`r` はデコード済みの入力です。
成功時にmessageを返し、エラー時にgRPC statusを返します。
ただし、cancelを確認した直後にcancelされる競合はあり得ます。これだけで決済の取り消しは保証しません。

## Streamingを追う

- server streaming: `Send()` を繰り返し、最後に `nil` を返す。
- client streaming: `Recv()` を繰り返し、`io.EOF` で送信終了を確認して `SendAndClose()`。
- bidi: `Recv()` したリクエストごとに `Send()`。同じstream内でやり取りを続ける。

client streamingの空入力は0件・0円です。同じ注文IDを2回送れば2件として集計します。
streamの最大入力件数は1,000件。状態を配列へ全件保存せず、件数と合計だけで集計します。

## 並行処理

gRPC-Goは複数のリクエストを並行処理します。
`map` の読み書きだけを個別に保護しても、存在確認と保存の間に別のリクエストが入ることがあります。
`Store.Pay()` は**keyの確認から決済保存まで**を1つのmutexで保護します。
`go test -race ./...` と、同じkeyを32件同時送信するテストで検証します。

## 直接コマンドで実行

生成とビルドはリポジトリrootで `python3 scripts/dev.py setup` と `build` を実行してください。
その後:

```bash
cd go
go test -race ./...
go run ./cmd/server
```

別ターミナル:

```bash
cd go
GRPC_TARGET=localhost:50052 go run ./cmd/client
```

接続は `grpc.NewClient()`、期限は `context.WithTimeout()` を使用します。
チャネルはRPCごとに作らず、クライアント処理の間は再利用します。
